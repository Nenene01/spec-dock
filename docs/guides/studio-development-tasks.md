# Studio改善タスク

Studioを「ソースファイルを並べたツール」から、業務・API・データの仕様を読めるアプリへ育てるための作業順です。機能の受け入れ条件は[Studio閲覧体験](../../specs/features/studio-reader-experience.md)を参照してください。

## 現状の考察

従来の画面は、最初に件数とファイルパスを見せ、利用者に「どの形式を開くか」を選ばせていました。これは実装者には有用ですが、業務担当者が知りたい「何ができるか」「操作に何を指定するか」「どんな情報が残るか」とは順序が異なります。また、Documentの見出しと概要の重複、分割ペインでの広い表、技術用語中心の見出しが読む負担になっていました。

今後は、業務文書を入口にし、明示された関連情報だけをつなぎます。閲覧者には内容と制約を先に見せ、定義元の形式・パスは確認したいときに開けるようにします。編集機能や自動要約によって正本が増えない構成を維持します。

参考にした考え方: [Backstage TechDocs](https://backstage.io/docs/features/techdocs/creating-and-publishing/)はコードと並ぶ文書の公開、[Redoc Community Edition](https://github.com/Redocly/redoc)はナビゲーション・本文・入出力例の役割分担を示しています。SpecDockではこの考え方を、Prisma・Zod・OpenAPI・Markdownを横断して読む用途に適用します。

## P0: 閲覧の入口と可読性

- [x] 概要を利用者の問いから選べる入口にし、実項目へ直接遷移する
- [x] 参照ソースを補助情報として整理する
- [x] 日本語の文字組み、詳細画面の行幅、狭いペインの表表示、フォーカス表示を整える
- [ ] Overview / Document / API / データモデル / ER図をデスクトップと分割ペインで目視確認する

## P1: ソース間を迷わず移動する

- [x] DocumentのAPI参照を、文書ヘッダー直下から開けるようにする
- [ ] APIのリクエスト・レスポンスから該当データ型へ移動できる範囲を検証し、不足を埋める
- [ ] データ型から参照元API、データモデルからER図の対象へ戻れるようにする
- [ ] 関連付け不能・複数候補・未定義のときの表示を定義する
- [ ] 各詳細画面で定義元の形式とファイルを一貫した位置から確認できるようにする

## P2: 探しやすさと品質保証

- [ ] 横断検索を設計する（Document本文、API名・パス、型、モデル）。過去に削除したサイドバー検索とは別に導線を検討する
- [ ] Studioの主要な閲覧・タブ移動・分割操作をブラウザE2Eで検証する
- [ ] 1280px、分割ペイン、狭い画面での視覚回帰を追加する
- [ ] コンポーネントとCSSを役割別に整理し、重複する上書き規則を解消する
- [ ] 空状態・読み込み失敗・解析できないソースの伝え方を統一する

## 判断基準

機能追加ごとに、非エンジニアが最初のクリックから目的の仕様へ到達できるか、元ソースが確認できるか、分割状態でも読めるかを確認します。

目視確認では、初めて触る人が「注文作成の条件」「POST /ordersの入力」「Orderの関係」をそれぞれ概要から2クリック以内で見つけられるかを記録します。サンプル固有の名称は測定用であり、Studioの実装には埋め込みません。
