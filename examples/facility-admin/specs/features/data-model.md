# データモデルの読み方

組織を境界にした施設・予約・管理操作のモデルと制約を説明する。

## エンティティの役割

| モデル | 用途 | 主なキー・制約 |
| :--- | :--- | :--- |
| Organization | 管理対象の組織 | ID |
| Operator | 担当者と権限 | 組織ID＋ログイン識別子が一意 |
| Facility | 予約を受ける施設 | 組織ID＋施設コードが一意 |
| Space | 施設内の区画 | 施設ID＋区画コードが一意 |
| Reservation | 区画の利用予約 | 組織ID＋予約番号が一意 |
| Announcement | 管理画面からの案内 | 組織IDと公開状態で検索 |
| ImportJob | CSV取込の進行状態 | 組織IDと状態で検索 |
| AuditEvent | 管理操作の記録 | 組織IDと発生日時で検索 |

## 関係と検索

組織は施設・予約・お知らせ・取込ジョブ・監査履歴を所有する。施設は複数の区画を持ち、予約は施設と区画の両方に結び付く。担当者はお知らせを作成し、監査履歴の操作主体になる。

通常の一覧検索はトークンの組織IDで絞り込み、施設は `deletedAt` が未設定のものに限る。予約一覧は組織、状態、開始日時に対する複合インデックスを想定する。

## Prisma Schemaだけでは表せない条件

- 予約の `startsAt < endsAt`、区画の `capacity > 0`、CSVの受付件数の整合などは、実DBでCHECK等を追加する候補。ここではAPIバリデーションとしても定義する。
- 実DBのRLS、トリガー、COMMENT、パーティションはこの論理モデルだけでは確認できない。
- `organizationId` と関連先の組織が一致するかは、APIの処理条件として確認する。単純な外部キーだけでは十分でない。

実際の型とインデックスは[Prisma Schema](../../prisma/schema.prisma)を参照する。
